The short answer

Nothing existing replicates Tahoe Mission Control end to end on Hyprland 0.56.2. Two compositor plugins get close on layout and animation, one Quickshell plugin gets the animation right but is welded to Omarchy, and the shell you already run ships the base architecture with the two hardest pieces missing.

gloview is the closest single project: live previews, a spaces strip and a current-workspace exposé shown together, per-window flight from the real screen rect on open, drag-and-drop between workspaces, extensive theming, an AUR package. It has no trackpad gestures, works per monitor only, and has no version pin at all. hymission covers gestures and multi-monitor and shows strip plus exposé by default, but its own README says it is almost entirely machine-written and internal docs contradict it.

DankMaterialShell already contains a Hyprland workspace overview in its core modules, present in both the stock and patched trees on this machine: fullscreen overlay layer, live thumbnails per window, spring animation, drag-and-drop onto workspace tiles, click to focus. It lacks the exposé spread, the continuous open animation from real window positions, and a first-frame gate. Those three gaps are exactly the Mission Control feel you described.

The feasibility analysis ranks extending that DMS overview first, with a tiny hook-free plugin as a fallback if one experiment fails: whether a video on an inactive workspace keeps playing inside a shell-captured thumbnail. Hyprland renders such windows off-screen on demand but only sends frame callbacks to the active workspace, so the thumbnail may freeze on its last frame. Compositor plugins dodge this by briefly marking each workspace active while rendering. That experiment can be run today with the built-in overview and decides the architecture.

What is already on this machine

DMS 1.6.0 (git c1f1da1) ships Modules/WorkspaceOverlays/ with three files: HyprlandOverview.qml (301 lines), OverviewWidget.qml (510) and OverviewWindow.qml (173). Both the stock cache and your patched shell tree carry them. Nothing in your hyprland.lua binds it, so it has never been opened here.

Verified by reading the source:

  • One PanelWindow per screen on WlrLayer.Overlay with namespace dms:workspace-overview, exclusive zone off, keyboard focus grabbed through HyprlandFocusGrab.
  • Every window is a ScreencopyView with live: true, capture source set only while the overview is open, geometry read from HyprlandToplevel.lastIpcObject and scaled into its workspace tile.
  • A rows-by-columns workspace grid from overviewRows, overviewColumns and overviewScale settings; four spring motions on x, y, width, height.
  • QtQuick Drag on windows and DropArea on workspace tiles, dropping through the DMS Hyprland service to move a window; click to focus, middle-click to close.
  • IPC exists: dms ipc call hypr toggleOverview plus openOverview and closeOverview.

What it does not do: spread the current workspace's windows so they stop overlapping (windows sit at their real relative positions inside the tile), animate windows from their true on-screen rects into the overview (it fades in and scales a whole tile), or wait for hasContent before showing a thumbnail (no occurrence in the directory, so a blank first frame is possible).

Try it before building anything. Bind or call dms ipc call hypr toggleOverview with a video playing on a workspace you are not looking at. If the thumbnail moves, the shell route is clear. If it freezes, the project needs the small compositor-side frame-tick plugin described in the architecture section. This is a visible desktop action, so it runs on your keyboard, not from an agent session.

Compositor plugins

C++ plugins loaded into Hyprland. They render workspaces inside the compositor, so every thumbnail is genuinely live, including inactive workspaces. The price is an ABI that must match the exact Hyprland commit, and a crash that takes every window with it. The official hyprexpo was deleted from hyprland-plugins on 2026-05-12, which is why this space fragmented into a dozen rewrites over the last four months.

How the plugins actually render

hyprtasking, and the projects derived from it, do not use off-screen framebuffers. They inject render-modifier passes with translate and scale into the live frame and temporarily set monitor->m_activeWorkspace to each workspace in turn, because, in the code's own comment, Hyprland only fully renders the monitor's active workspace. That trick is what makes every thumbnail live, and it is the one thing a shell overlay cannot reproduce. Drag-and-drop hijacks the layout manager's drag controller and warps the pointer. hyprtasking installs seven mangled-symbol hooks; any signature change aborts the plugin at load. Its compatibility header regenerates ABI macros from the live aquamarine, hyprutils and hyprlang versions, so an aquamarine bump alone breaks it.

All four of the closest plugins document Lua bindings under the 0.55+ config runtime, registered through HyprlandAPI::addLuaFunction and surfaced as hl.plugin.<name>.toggle(), so a Lua config is not an obstacle on that route.

Shell-level overlays

Layer-shell windows that capture each toplevel with Quickshell's ScreencopyView and compose the picture in QML. No compositor risk, full access to your matugen palette and DMS chrome, plain QML drag-and-drop. The thumbnail of a window is the window's own buffer, so it is live wherever the compositor keeps rendering it.

What Hyprland allows

Core and maintainer stance

  • No release from 0.51.1 through 0.56.2 adds a native overview. Issue #1902 settled it: the maintainer exposed render hooks for plugin authors and declared overviews plugin territory.
  • 0.54 added ext-image-capture-source-v1 and ext-image-copy-capture-v1; hyprland-toplevel-export-v1 is still present and not deprecated.
  • 0.55 added the Lua config runtime and spring animations. 0.56 added Lua-driven custom live gestures (hl.gesture) and xdg interactive drags.
  • Plugin ABI: HYPRLAND_API_VERSION is a constant string; real compatibility is hyprpm matching the exact commit hash. Headers are installed under /usr/include/hyprland.

The Lua runtime

  • Can: bind keys, dispatch, subscribe to events, run timers, move and resize windows, set noanim and other props, pin, float, define gestures, register a custom layout provider, and call plugin functions.
  • Cannot: draw anything, receive pointer or drag events, or capture the screen. A real exposé done by moving the real windows works for one window (your carry.lua) and breaks tiling, split ratios and fullscreen state for fourteen.
  • The stub-generated API list the agent produced omitted hl.animation, hl.curve and hl.plugin.load, all of which your config uses on 0.56.2, so treat that list as a floor.

Live capture facts, verified in source

  • Toplevel export renders a window off-screen on demand with no visibility early-out (ScreenshareFrame.cpp, standalone render). Hidden and inactive-workspace windows do get captured.
  • Frame callbacks reach only the active workspace and active special workspace (Renderer.cpp, sendFrameEventsToWorkspace). A client on an inactive workspace is not told to paint, so its capture likely repeats the last frame. Unproven either way in the field.
  • Quickshell's screencopy manager accepts only a screen or a toplevel as a source. There is no workspace capture; whole-workspace thumbnails are composed from per-window captures.
  • Each captured frame is a full re-render at the window's native resolution. No scaled capture exists. Estimated 2 to 6 ms of extra GPU time per frame for this machine's window count, unmeasured.
  • quickshell #1123, open, filed against 0.3.1 and Hyprland 0.56.2: concurrent live views can race the Wayland id allocator and take down the whole shell. Needs four or more windows and repeated open and close.
  • Only the first frame schedules a compositor frame; an idle overlay stops committing and every thumbnail freezes. Keep one animating pixel alive.
  • no_screen_share is a real rule key for excluding the overlay from captures. ignorezero does not exist in the source.

DMS plugin system

  • Manifest types are widget, daemon, launcher, desktop and composite. No fullscreen surface type, no documented IPC or keybind registration for plugins.
  • A daemon plugin's QML is a plain Item with no sandbox, so it could plausibly create its own layer-shell window. Unverified and unsupported. The supported route is a core-module change, which your dms-shell-patch pipeline already does.

Architecture options, ranked

  1. Extend the DMS workspace overview

    shell overlay · Quickshell · no compositor risk

    Add an exposé layout pass for the focused workspace, seed each thumbnail at its real rect before the overlay becomes visible so the open animation is continuous, gate visibility on hasContent with a short watchdog, refresh toplevel geometry before showing, stagger capture creation to dodge the id race, and drop the capture rate off-hover to control GPU cost. Drag-and-drop, springs, focus grab and multi-monitor are already there. Chrome takes the matugen palette for free. The seam between real windows and thumbnails cannot be made atomic from a client, so a one-frame join is the residual risk to measure, not guess.

  2. The same, plus a hook-free frame-tick plugin

    hybrid · ~50 lines of C++ · degrades safely

    If the deciding experiment shows inactive-workspace thumbnails freezing, a tiny plugin that ticks frame callbacks for the windows being viewed while the overview is open fixes exactly that defect. No render hooks, no mangled symbols, so an ABI break means it fails to load and the overview still works with stale inactive thumbnails. A full hybrid that hands compositor textures to Quickshell has no cheap path and merely relocates the seam.

  3. A full compositor plugin

    C++ · fork gloview or hymission · live everything, seamless handoff

    The only route with guaranteed-live inactive workspaces and a truly seamless open, because the compositor draws both the real windows and the overview in one frame. Against it: exact-commit ABI matching with a rebuild after every Hyprland or aquamarine update, a crash kills the compositor, and no plugin can host DMS-style text, fonts or palette. If you go this way, fork gloview for its animation and issue hygiene or hymission for gestures and multi-monitor rather than starting from hyprtasking's grid.

  4. Lua-only exposé of the real windows

    fallback only

    Floating and moving every tiled window on a timer causes configure storms, loses dwindle ratios and never shows other workspaces. The unexplored alternative is the Lua layout provider (hl.layout.register), which nobody has evaluated for animated targets.

The macOS target, as a checklist

Trigger and exit

  • F3 or Control + Up, three-finger swipe up (four-finger optional), hot corner, Dock icon. Exit with the same trigger, Escape, or a click. Shift held slows the transition.
  • App Exposé is Control + Down, current app only, Tab cycles apps. Command + F3 is Show Desktop, a different thing.

Spaces bar

  • A thumbnail for every Space and every fullscreen or Split View app, not for ordinary windows.
  • Inactive entries collapse to labels and expand on hover; a plus button appears on hover at the right edge; hover shows a close button; drag to reorder is widely reported but not in Apple's current docs.
  • Displays have separate Spaces is on by default, and Mission Control is invoked per display, not as one overlay across monitors.
  • Whether the Space thumbnails refresh live while open is unverified either way. Treat it as your design choice.

Exposé area

  • Windows of the current Space scaled uniformly, aspect preserved, pushed apart until none overlap, kept near their original positions. That description comes from Apple's 2003 Exposé patent (US 8,127,248), not from a published Tahoe algorithm.
  • Group windows by application clusters per app. Minimised windows are excluded from the main grid, hidden apps excluded entirely, fullscreen apps live in the top bar only.
  • Titles on hover, arrow-key navigation, spacebar Quick Look on a thumbnail.

Interactions and motion

  • Click a window to switch and exit, click a Space to switch, drag a window onto a Space to move it, drag onto the plus button to seed a new Space, Control + Left or Right to change Space.
  • Windows fly continuously from their real positions; no cut. Duration and easing are not published anywhere; the only community figure is a stale 0.2 to 0.25 s guess.
  • Tahoe specifics: a Liquid Glass pane descends and refracts the wallpaper on open; 26.1 added the Clear or Tinted glass toggle; 26.4 removed a drop shadow from the Mission Control view. Apple's release notes for 26.0 through 26.6 do not mention Mission Control otherwise.

Reference implementations to read

  • GNOME Shell js/ui/workspace.js, UnalignedLayoutStrategy.computeLayout: iterative row-count search, greedy row packing by original vertical position, one uniform scale. The best-documented exposé algorithm and the one to reimplement in QML.
  • niri overview (v25.05): live zoomed-out rendering, non-blocking animation with input working mid-transition, drag between workspaces, pan and scroll. Config in niri-config/src/misc.rs, runtime in src/niri.rs and src/input/touch_overview_grab.rs. The closest native Linux equivalent to Mission Control.
  • COSMIC cosmic-workspaces-epoch: an out-of-process overview built on screencopy and DMA-BUF with pluggable layouts under src/widgets/toplevels/toplevel_layout/. The same shape as the shell-overlay route on Hyprland.
  • KWin src/plugins/overview: QML effect with live window heaps, cross-desktop drag, type-to-search, and a new strip-packing layout under review.
  • hyprtasking src/render.cpp and src/input.cpp: how a plugin renders every workspace live and hijacks drag, if the plugin route is ever taken.

Questions only a prototype answers

In priority order. The first one decides between the top two architectures and can be run with the overview DMS already ships.

  1. Does a video keep playing in a thumbnail of a toplevel on an inactive workspace? Loop mpv on one workspace, open the overview from another, watch for motion. Repeat with Chromium and an XWayland app.
  2. Does a window fully covered by the overlay on the active workspace keep painting, or does occlusion culling route it through the discard path?
  3. What do 14 to 20 simultaneous live captures cost at 5120 by 1440 at 120 Hz on the RX 6600, live versus timed stills? Measure frame time with both monitors attached.
  4. Can quickshell #1123 be reproduced here, and does staggering capture creation avoid it?
  5. How many frames does the open handoff flash? Count from Hyprland frame logs the way the DMS theme-sync work did, never by eye.
  6. Do XWayland toplevels export frames at all, and does their reported geometry match the real rect under scaling?
  7. Is the DMS Quickshell instance already granted the screencopy permission, or does a fresh capture prompt?
  8. Can the Lua layout provider express an animated exposé without destroying dwindle split ratios?
  9. Does the plugin trick of momentarily activating a workspace fire IPC events that make the DMS bar flicker?
  10. Can a QML drag cross between the two per-screen panel windows, or does it die at the monitor edge?
  11. After a drop and workspace switch, is the correct window focused once the layer's keyboard grab releases?
